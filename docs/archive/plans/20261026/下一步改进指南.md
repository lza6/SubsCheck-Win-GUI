## 5. 方案对比（≥3 种）

| 维度 | 方案 A：保守加固（传统） | 方案 B：渐进模块化（优化，推荐） | 方案 C：迁移 .NET 8 + MVP/MVVM 重写（创新） |
|---|---|---|---|
| 内容 | 只修 P0/P1：密钥、HttpClient 复用、状态机、catch 加日志，不动结构 | 先做 A，再按内聚度逐块从 Form1 抽出：ConfigService、ProcessManager、ProxyPoolService、GitHubClient；Form1 只留 UI 绑定 | 升级 .NET 8 WinForms，引入 CommunityToolkit.Mvvm，配置/进程/代理全部服务化，补测试与 CI |
| 技术可行性 | 高 | 高（每次抽取可独立编译验证） | 中（Designer 文件迁移需处理，packages.config→PackageReference） |
| 开发成本 | 低（1-2 天） | 中（1-2 周，可分多次会话） | 高（3-4 周起） |
| 维护成本 | 仍高（4600 行继续膨胀） | 显著下降 | 最低 |
| 风险 | 最低 | 低-中（每次抽取是可回滚小步） | 高（一次性大改，回归面大） |
| 用户便捷性/SaaS 成熟度 | 不变 | 提升（稳定性、可观测性） | 最大（自动更新、日志、性能） |
| 80% 轮子复用 | DPAPI、HttpClient 静态实例 | 同 A + 标准分层 | 同 B + CommunityToolkit |

关键决策因素：本项目是活跃使用的 GUI 工具，用户要"稳定可用"而非"架构漂亮"；fork 与上游存在同步需求，大改会增加合并冲突。

## 6. 推荐方案与理由

**推荐方案 B（渐进模块化）**：先执行 A 的全部 P0/P1 修复（风险最低、收益立现），随后以"每次只抽一个服务类、抽取后立即构建+手测该功能"的原子节奏推进。不选 A 是因为它不解决 Form1 持续膨胀的根因；不选 C 是因为一次性重写违反本项目"禁止大幅重构/重写"红线且回归风险不可控。B 的每一步都满足"可独立验证、可回滚"。

## 7. 版本迭代路线

- **v1.0.1（安全与稳定 hotfix）**：P0-1 密钥随机化、P0-2 DPAPI 加密凭据（兼容旧明文自动迁移）、P0-3 状态机替换按钮文字判据、P1-1 单例 HttpClient（静态复用 + 每请求超时）、P1-5 按架构下载 x64/x86。→ 价值：安全收口、长期运行不崩。
- **v1.1（可观测性）**：统一日志（Serilog 或简单文件 logger，替换 3 处空 catch 为 `Log(ex)`）、config 写入加锁（SemaphoreSlim）、异常上报到现有 Log 面板。→ 价值：故障可诊断。
- **v1.2（配置模型）**：强类型 Config POCO + YamlDotNet 类型化序列化，替换 Dictionary 手解析；UI 控件值↔模型单向绑定函数化。→ 价值：消灭 P2-3 一类解析 bug。
- **v1.3（模块抽取 1/2）**：抽 `ConfigService`、`GitHubClient`（版本检查/下载/代理前缀统一），Form1 调用服务。构建+冒烟验证。→ 价值：Form1 首次减重 ~800 行。
- **v1.4（模块抽取 2/2）**：抽 `ProcessManager`（内核启停/清理）、`ProxyPoolService`（代理测速与轮换，含 50/1000 节点间隔逻辑）。→ 价值：核心复杂度出窗体，可被单测。
- **v1.5（质量基建）**：抽 Core 类库项目（net472），建 xUnit 测试工程覆盖 ConfigService/ProxyPoolService 纯逻辑；加 GitHub Actions：msbuild + nuget restore + 测试。→ 价值：回归有护栏。
- **v2.0（可选，需用户拍板）**：评估 .NET 8 迁移与 PackageReference（方案 C 的温和版：仅框架升级不动架构）。→ 价值：现代 API、性能；仅在 v1.x 稳定后启动。

> 每步均有实质价值，无"为升版本而升版本"项；v2.0 前设用户决策点。
