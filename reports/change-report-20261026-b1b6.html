1. 上下文（为什么做）

v2.0.2 终局审计后，Form1.cs 膨胀至 4715 行，承担 9 类职责：日志仅内存、输出解析内联且无内核文案变更告警、config.yaml 整体重写会覆盖用户手写字段、零测试、GUI 崩溃会留下孤儿内核进程。上游分析报告（六维评分路线图）给出 B1-B6 六个可独立回滚的改造批次，本轮全部落地。

2. 直觉与关键取舍

  • 零新运行时依赖：日志库不引入（内置 2MB×3 轮转）；测试用 MSTest（仅测试项目引用），保持便携形态。
  • 薄委托而非调用点全改：Cron/config 读取辅助在 Form1 保留一行委托，调用点零改动，回滚=删文件。
  • 读-改-写优先于 schema 全量建模：ConfigService 以 Dictionary 为中心，手写字段天然保留，避免维护完整配置模型与内核漂移。
  • 未知行告警去噪：审查发现逐行告警会污染日志，改为聚合计数、每次运行仅提示一次。

6. 风险与回滚

  • 风险1：未知行告警初期可能误报非常规内核日志 → 已去噪（计数+单次提示），如需彻底关闭可注释 Form1.cs 告警块。
  • 风险2：YamlDotNet 序列化 Dictionary 的类型标注（类型前缀）可能影响内核解析 → 测试覆盖 bool/int/List 往返；真实 config 冒烟通过（内核未启动验证，标注为边界）。
  • 风险3：Job Object 句柄由 GUI 进程持有，GUI 正常退出时 OS 自动关闭 job → KILL_ON_JOB_CLOSE 触发，属预期行为；P/Invoke 签名经独立审查。
  • 回滚：单 revert 任一 Service commit；B5 有运行时开关 ProcessSupervisor.DisableJobObject=true。

7. 已知限制

  • 覆盖率未测量（.NET Framework 4.7.2 无 coverlet，需 Core 类库迁移）
  • 内核真实测速链路（含订阅源）未跑全流程，需真实环境
  • 16 处 new HttpClient 未复用：既有 backlog（中型重构，未授权）

8. 交付测验（自测）

Q1（选择）：用户手工在 config.yaml 加了 custom-field: keepme，GUI 保存后该字段会？
A. 被删除 B. 被覆盖为空 C. 保留（读-改-写）✔ D. 移入 more.yaml
答案与解析C。ConfigService.Save 先 Load 现有配置再覆盖 updates 中的键，未提及键原样保留。测试 Config_ReadModifyWrite_PreservesUnknownFields 验证。
Q2（判断）：GUI 进程被任务管理器强杀后，subs-check.exe 会继续运行成为孤儿进程。
答案错。ProcessSupervisor 将内核绑定到 KILL_ON_JOB_CLOSE 的 Job Object，GUI 句柄关闭时 OS 终止内核。
Q3（简答）：内核 subs-check 升级改了输出文案，GUI 如何表现？如何排查？
答案解析器将该行标记为 IsKnown=false，首次出现时日志输出一条「⚠️ 检测到未识别的内核输出（聚合计数）」告警（后续静默计数），指引用户在 SubsCheckOutputParser.KnownMarkers 登记新文案。进度/下次检查时间等已知模式不受影响。
Q4（选择）：B5 需要临时回退旧行为，正确方式？
A. 卸载 GUI B. ProcessSupervisor.DisableJobObject = true ✔ C. 删除内核 D. 改注册表
答案B。运行时开关，无需重编译回滚。
Q5（判断）：日志文件写满 2MB 后程序会停止记录。
答案错。RotateIfNeeded 触发 log → log.1 → log.2 → log.3 轮转，最旧丢弃，持续记录。
